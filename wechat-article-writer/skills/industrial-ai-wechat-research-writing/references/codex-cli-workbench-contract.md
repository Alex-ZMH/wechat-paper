# Codex CLI 内容工作台契约

本文件只在内容工作台通过 Codex CLI 生成初稿或按批注重生成时读取。目标是证明请求真实进入模型、保护作者手改，并在协议失败时不覆盖原稿。

## 1. 固定链路

工作台只允许：浏览器 → 绑定 `127.0.0.1` 的受限内容桥接 → `codex exec`。公网托管端不保存或执行本机凭据，不开放通用 prompt、命令或文件接口。初稿和重生成调用同一内容端点；禁止在 Codex 不可用时切换到模板、字符串替换或确定性规则。

桥接只接受两种 `mode`：`initial_generation` 与 `annotation_regeneration`。运行 Codex 时使用非交互、临时会话、只读沙箱、无需审批和 JSON Schema 约束；工作目录固定到本项目。服务只绑定回环地址，限制允许的浏览器 Origin、请求体大小、超时和并发，不把 CLI 日志、路径、凭据或完整提示词返回前端。

## 2. 作者修改台账

重生成必须同时接收：

- `previousGeneratedDraft`：上一版模型生成稿；
- `currentDraft`：用户当前修改稿，也是本轮权威底稿；
- `annotations`：只含活动批注；
- `brief`、`voiceProfile`、目标长度、受保护事实和版本标识。

写作前对比两稿，提炼而不是逐字符展示：

- 用户删除了哪些套话、结论或段落；不得无声补回；
- 用户新增或替换了哪些术语、对象、限制和立场；优先沿用；
- 用户怎样调整段落顺序、句长、标题和判断强度；作为声音信号；
- 哪些修改可能与批注、证据或受保护事实冲突；先标出再处理。

活动批注可以改变受影响内容，但回执必须说明。没有批注时，只要两稿不同，也允许按作者修改台账继续生成。模型认为必须推翻某项手改时，只能因明确事实冲突、内部矛盾或批注明示，并在 `preservedUserEdits`/`unresolved` 中披露，不能直接还原旧稿。

## 3. 两阶段生成

第一阶段由写作者形成候选稿，必须先解决事实边界和批注，再处理表达。第二阶段由质量审阅者拿到简报、两稿、修改台账、活动批注和候选稿，逐项检查：

1. 是否把相关性写成根因、把厂商声明写成独立事实；
2. 是否保留作者手改并逐条处理批注；
3. 是否回答了工业场景中的数据、分析、动作、权限、流程和验收；
4. 是否出现空泛开头、模板套壳、假亲历、机械排比或无对象的管理词；
5. 是否新增无来源数字、案例、引语、标准全称或效果保证。

人的声音检查必须验证“延续”而不只是“保留”：如果作者手改了句长、判断顺序、常用词或判断强度，候选稿后半段至少有 3 处可观察的同类延续。短中篇稿通常不超过 4 个一级/等效小标题，同一证据字段模板不得机械重复 3 次；明显超出目标长度时先删重复。缩写首次出现写中文含义，能用准确白话说明的概念不靠术语堆砌。

第二阶段必须直接返回修订后的完整稿和审计结果，不能只写评语，也不能列出未修问题后仍返回 `passed=true`。若第二阶段失败或仍有高风险问题，桥接返回错误；前端保留原稿、手改和批注，不得把候选稿包装成“已通过双阶段复审”。

第二阶段还必须返回可解释的 `qualityReview.editorialScore`，不能只给一个 `humanVoice=true`。评分五项满分固定为 `factualBoundaries=25`、`specificActionability=25`、`authorVoiceContinuation=20`、`antiTemplateVariation=20`、`mobileClarity=10`；每项带 `score`、`max`、`reasons`，并用 `deductions[{dimension,points,reason}]` 逐项解释扣分。服务端校验分项范围、总分等于分项之和、扣分等于 `100-total`，第二阶段 `total>=95` 才能通过。评分是编辑 rubric，不是 AI 检测概率或规避器；确定性反 AI 扫描、事实不变量和作者修改保护任一失败，即使模型自报 100 也拒绝。

## 4. 专业方案最低证据结构

针对“问题多发、并不指向单一站点”这类问题，至少覆盖：

- 用站点、产线、产品/批次、工序、设备、缺陷、时间、配方/程序版本形成可关联的事件主键；频次按产量、批次或运行时长归一化；
- 先区分测量系统问题、数据口径不一、局部特殊因和跨站点共因，再排列候选假设；
- 每个高优先级假设附支持证据、反证、缺失字段、下一步验证和责任角色，不把聚类或相关性写成已确认根因；
- 说明智能体可做的取数、归并、假设排序、证据包、建单和提醒，以及隔离、停线、改参数、冻结批次、放行等必须人工审批的动作；
- 说明如何进入 8D D2–D4、CAPA、PFMEA/控制计划，不另造平行流程；
- 试点先历史回放再影子运行，验收使用输入可计算的 MTTD、误报、工程师采纳、证据可追溯、处理时长或复发指标。无基线时不写百分比承诺。

## 5. 返回与前端验收

返回对象至少包含：`draft`、`versionId`、`receipts`、`diagnostics.engine="codex-cli"`、`diagnostics.remainingFlags`、`editorialMemo.preservedUserEdits` 和 `editorialMemo.unresolved`。每个活动批注 ID 必须恰好出现一次，不得缺失、重复或返回未知 ID。

导入外部文章时仍使用 `annotation_regeneration`：首次导入可将 `previousGeneratedDraft` 与 `currentDraft` 设为同一篇外部原文，随后只消费活动批注。`currentDraft` 始终是权威稿；外部原文的数字、引语、URL、专名和用户后续改动仍按同一不变量规则保护。

前端在覆盖稿件前验证：正文非空、引擎来源、回执集合、作者修改保护报告和请求期间版本未变化。成功时同时把本轮前的 `generatedDraft`、`editedDraft`、完整批注、时间和版本号存入历史；撤销必须恢复双轨状态。任何网络、权限、CLI、Schema、审阅或并发冲突失败，都保持正文、批注和版本号不变。
