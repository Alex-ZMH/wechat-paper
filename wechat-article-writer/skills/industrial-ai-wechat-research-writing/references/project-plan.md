# 工业向公众号调研写作项目规划

## 目标

建立一个证据优先的工业调研写作工作流，帮助个人开发者持续产出关于工业智能体、工业/科研大模型、工业软件和质量过程工具的可读文章。每篇文章都能回到来源、截止日期和未决问题，而不是依赖模型的“知道”。

## 非目标

- 不做自动登录、采集私域/付费墙、绕过验证码或批量爬取。
- 不复制任何置顶项目、GitHub 项目代码、文案、CRM、采集器、桌面架构或发布流程；置顶项目只参考访问安全、审批边界和分层思想。
- 不承诺自动排版、发布、群发、阅读量、ROI 或客户效果。
- 不把政策目标、厂商路线图或单个案例写成已经实现的普遍成效。

## 受众

制造企业数字化负责人、工艺/质量/计划人员、研发与科研工程师、工业软件实施者，以及希望理解工业 AI 但不想被营销术语带走的技术管理者。写作默认解释背景和边界，允许专业读者指定更深的术语密度。

## 栏目矩阵

| 栏目 | 核心问题 | 证据优先级 | 推荐形态 |
| --- | --- | --- | --- |
| 工业智能体与模型 | 能做什么、不能做什么、部署条件 | 官方文档/标准/论文，再看厂商公告 | 快讯、工具速览、深度调研 |
| 研发/科研工业化 | 模拟、优化、材料/实验闭环如何落地 | 论文、项目文档、公开案例 | 标准解析、案例复盘 |
| VASP/HPC 与科研算力 | 工作负载和硬件配置是否匹配、许可证与测试边界 | 用户测试条件、官方规格/许可证入口、论文与可复现实验 | 工具速览、采购核对、论文分享 |
| MES/MOM/APS/ERP/SCADA | 系统边界、数据链路和集成责任 | ISA-95、厂商产品页、实施文档 | 标准解析、对比文章 |
| 质量与过程工具 | FMEA、8D、APQP、PPAP、SPC、MSA 的使用边界；处理 FEMA/FMEA 和 6A 歧义 | AIAG/VDA、ASQ、API/ISO、国家/行业标准 | 教程、标准解析、案例复盘 |

### FEMA/FMEA 与 6A 术语路由

- 制造质量强语境下把 `FEMA` 透明规范为 FMEA，首次说明用户原文拼写；企业内部自定义 FEMA 保留原词并核对全称、版本和来源；灾害/应急/美国机构语境保留 FEMA 机构名，弱语境只追问。
- FMEA 文章说明前置技术风险分析、AIAG/VDA 七步，以及 DFMEA、PFMEA、FMEA-MSR 边界；付费手册不做完整摘要，旧 RPN 与新 AP 不混为固定规则。
- `6A` 不统一补全：DMAIC/波动/西格玛水平走 6σ；井口/采油树/PSL 走 API Spec 6A；铁路安全防护线索走机车 6A 系统；企业自定义 6A 只标 `vendor_claim/company_specific`；无语境时分别给每个缩写不超过 3 个候选并只问一个短问题。

## 工作流

选题简报 → 检索计划 → 来源筛选 → research packet → claim ledger → 冲突/时效检查 → 文章草稿 → 事实/表达/移动端审校 → 人工决定是否排版或发布。每一阶段都可以停在 `partial`、`blocked` 或 `manual_required`，不要为了“完成”而补齐未知内容。

## 里程碑

1. M1：领域 taxonomy、来源注册表和访问政策可用，术语歧义有处理规则。
2. M2：packet schema、标准库校验器和失败 fixtures 可运行。
3. M3：至少完成一个有截止日期和来源台账的工具速览、一个标准解析和一个深度调研样稿。
4. M4：用 harness cases 复盘厂商主张、访问失败、证据冲突和长度决策；根据失败补规则而不是补黑名单。

## 验收标准

- 事实主张有可用来源；blocked/manual_required 来源不能支撑事实。
- vendor_claim 明确厂商身份，不能冒充独立效果证据。
- 术语歧义（FEMA/FMEA、6A）被澄清或标为未决。
- 文章披露截止日期、覆盖范围、限制和未核实项；深度调研不固定 500 字。
- 访问受阻时停止并给出替代来源或人工取回路径。
- 术语路由评测覆盖制造质量 FEMA 自动透明规范化、灾害 FEMA 保留、6σ、API Spec 6A、铁路 6A、企业自定义 6A 和无语境追问。
- VASP/HPC 文章必须列 CPU/GPU、内存、存储、互联、许可证、功耗/散热、规模和工作负载；商业字段有截止日期，未经基准测试不承诺性能/ROI。
- 计算+实验论文分享必须区分原始结论、转述、计算假设/DFT 结果、实验条件、相关性/因果、复现与外推；“吻合”不得升级为机理已证明。
- validator、harness 和 bundle validate 可重复运行。

## 个人开发者取舍

优先少而可靠的来源、可复查的短 claim 和小步迭代；宁可交付一篇范围有限的文章，也不维护脆弱的全网采集器。先做静态 HTML/PDF/官方 API/RSS，后续是否增加连接器取决于授权、维护成本和真实需求。

## 同类工具的能力对照（只看原则，不复制实现）

公开可见的 [wechat-skill](https://github.com/843645440/wechat-skill) 覆盖热点、写作核验、来源台账、排版和只建草稿；[wechat-article-pipeline-skill](https://github.com/jhwreal/wechat-article-pipeline-skill) 强调长文、配图、HTML 工作台和明确请求后才建草稿。它们说明“研究—人工核对—草稿—发布”应分层，本项目的差异是工业术语边界、claim ledger、厂商主张分层和访问 fail-closed。

[wxhou/wechat-article-writer](https://github.com/wxhou/wechat-article-writer/blob/main/SKILL.md) 的公开写法包含个人经历类套路，本项目不把个人经历设为固定模板，也不代写未提供的第一人称故事。[doocs/md](https://github.com/doocs/md) 是 Markdown 到微信图文的排版层，不是研究证据层。[baoyu-post-to-wechat](https://github.com/JimLiu/baoyu-skills/blob/main/skills/baoyu-post-to-wechat/SKILL.md) 只作为发布层分离的公开对照。这里只记录原创比较结论和链接，不复制代码、文案、CRM、采集器或桌面架构，也不写易变的星标/排名。
